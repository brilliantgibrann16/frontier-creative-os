# ADR-0010 — Concrete M-B Clause-Index Schema (P03.4)

**Status:** Accepted
**Date:** 2026-08-12
**Decider:** Maintainer (Constitution Article 6)
**References:** RFC-0008 (design space, OQ1–OQ3), ADR-0004 (M-B posture
ratification), ADR-0008 (N-B + N-C registry discipline), ADR-0009
(decision 4 — schema trigger), `specs/S04-language-definition.md`
(ratified container — Interfaces, Data model), Baseline §10, Blueprint
§7, RFC-0002, RFC-0009 (interim V-D), CN-14, CN-26,
`docs/program/DOC_DERIVATION_CONVENTIONS.md` §5, Issue #7

## Context

ADR-0004 ratified RFC-0008's recommendation as **posture only**:
prose-authoritative specifications with a machine-readable clause
index (M-B), resolving U-9 (posture). The concrete schema was deferred
to "first specification ratification" (RFC-0008 §Consequences), and
ADR-0009 decision 4 interpreted that trigger as the S04 container
ratification — making the schema the next authorized P03 decision item
while explicitly not inventing it. RFC-0008's Open Questions — (1)
which Doctrine §13 audits must be mechanical at first spec
ratification, (2) where the clause index lives, (3) whether the index
is normative or derived hygiene — had no recorded answers.

On 2026-08-12 the Maintainer decided the concrete schema explicitly
and in writing (a sixteen-point directive). This ADR is the
authoritative record: where ADR-0004 established the M-B posture, this
ADR establishes the concrete schema. It records the directive without
addition (CN-14): no Stage 0 clause, no clause ID, no namespace token
is created, and no S04 content is ratified.

## Decision

1. **Authority — derived hygiene (RFC-0008 OQ3, discharged).** The
   clause index is a machine-readable index of specification clauses.
   The specification prose remains authoritative; the index is derived
   from and mechanically checked against the prose and never overrides
   it. The index is **not** independently normative: it is hygiene and
   consistency infrastructure, not a second source of normative truth.
   Changes to specification prose remain governed by the normal
   RFC → ADR ratification path.

2. **Scope.** The index indexes ratified specification clauses only.
   Unratified / in-review material may appear only where lifecycle
   visibility requires it, explicitly marked non-ratified, and is
   never treated as authoritative. No entry may exist for a
   nonexistent clause; the S04 index is therefore legitimately empty
   until P03.3 establishes the Stage 0 clause inventory.

3. **Location — per-spec sidecar (RFC-0008 OQ2, discharged).** Each
   specification carries its own sidecar index colocated with it under
   `/specs`. For S04: `specs/S04-language-definition.index.yaml`. No
   corpus-wide clause-index file is created at this stage.

4. **Serialization — YAML.** Human-reviewable, machine-processable,
   diff-friendly, and consistent with the repository's
   documentation-oriented workflow; no proprietary tooling required
   (CN-26; RFC-0008 A-2).

5. **Minimum schema.**

   ```yaml
   spec:
     id: <spec ID>
     version: <spec/container version>
   clauses:
     - id: <clause ID>
       category: <category>
       title: <clause title>
       status: <lifecycle status>
       source: <authoritative source reference>
   ```

   Every clause entry requires all five fields: `id`, `category`,
   `title`, `status`, `source`. No text duplication, hashes,
   implementation fields, timestamps, owners, or other fields are
   added unless an existing ratified requirement explicitly requires
   them. Compatibility check recorded: the ratified S04 Data model
   attributes traceability links to the *clause* (the authoritative
   prose record); it does not require them in the index, so the
   five-field minimum stands without conflict.

6. **Identifier rule.** Clause IDs must conform to the ratified
   N-B + N-C scheme (ADR-0004; ADR-0008) and the freeze binding since
   the S04 container ratification (ADR-0009). The schema defines
   validation requirements only: it creates no identifier, no
   namespace token, and no clause ID before P03.3.

7. **Category vocabulary.** `category` uses the vocabulary the
   ratified container already enumerates: exactly one of `defined`,
   `implementation-defined`, `unspecified`, `undefined` (S04 Data
   model — "category (one of the four above)"; S04 Responsibilities;
   Baseline §10). This is a derivation from ratified text, not a new
   enumeration.

8. **Status vocabulary.** `status` distinguishes at minimum
   `ratified`, `in-review`, `deprecated`. The index must never
   represent an item as `ratified` unless the corresponding
   specification clause has passed its ratification path.

9. **Source.** `source` points back to the authoritative prose
   location in the specification; the prose remains the canonical
   source.

10. **Ordering.** Clauses are ordered by their ratified clause ID. The
    index introduces no independent semantic ordering.

11. **Maintenance / drift.** The index is mechanically checked against
    the specification prose. The repository must detect: missing index
    entries for ratified clauses; index entries with no corresponding
    authoritative clause; duplicate clause IDs; invalid category or
    status values; invalid identifier syntax; broken source
    references. **No such checker exists today** — `tools/checks/`
    holds `check_links.py` and `check_ids.py` only. The checker is
    recorded as a subsequent implementation task (follow-up 1), not
    pretended to exist.

12. **Mechanical audit set (RFC-0008 OQ1, discharged — narrow).** For
    the first specification ratification, the mechanical audits
    required for M-B are exactly the consistency checks of decision 11
    plus the existing repository link/ID integrity gates
    (`tools/checks/check_links.py`, `tools/checks/check_ids.py`). No
    additional Doctrine §13 audits are created by this decision.

## Consequences

- **RFC-0008 is fully discharged**: posture by ADR-0004, concrete
  schema and OQ1–OQ3 by this ADR. The RFC index disposition row
  (`docs/rfc/README.md`) is updated in this same change.
- **P03.4 is executed.** The S04 charter §2/§7 registers record it in
  this same change.
- **P03.5 remains blocked** — it depends on the drift checker
  (follow-up 1) and on an instantiated index with ratified clauses
  (P03.3).
- **The S04 sidecar is not instantiated in this change.** Two blockers
  are recorded rather than papered over: `spec.version` has no
  derivable value — no ratified specification-versioning scheme exists
  (RFC-0009 recorded only the interim language-version rule V-D, which
  governs the language, not specification documents) — and the clause
  list is necessarily empty before P03.3. Instantiation is queued as
  follow-up 2.
- **The ratified S04 text is not touched.** Its Interfaces statement
  "Schema: BLOCKED — … unblock: P03.4 at that ratification" now has
  its referent in this ADR, but S04 is ratified: post-ratification
  text change travels the amendment path (INV-18; S04 State machines),
  never a silent edit. Discharging that marker in the spec text is
  amendment work requiring its own Maintainer decision, not performed
  here.
- **No implementation is authorized** beyond recording follow-up 1 as
  a task. CN-14 stands.

   implementation task; P03.5 consumes it; not begun without its own

2. Instantiate `specs/S04-language-definition.index.yaml` once a
   `spec.version` value is decided (Maintainer decision — no ratified
   specification-versioning scheme exists today); its `clauses` list
   stays empty until P03.3.
3. Knowledge-mirror sync (P02.3; trigger: governance merge).
4. P03.3 — Stage 0 clause inventory decision (unchanged; still the
   controlling content gate).
