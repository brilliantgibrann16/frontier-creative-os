## Context

RFC-0020 (merged 2026-08-19 via PR #46, merge commit e4aa8905) drafted
the twelve-clause Stage 1 W-B interchange kernel that ADR-0012
follow-up 1 called for, reserved proposed identifier S04#8.3 for the
concrete interchange form, and presented two decision surfaces without
choosing: F1 (the concrete serialized interchange form — F1-A, an
existing boring standard per GL-15/DP-28, versus F1-B, a bespoke
form) and F2 (sequencing — path 1 revise-then-ratify versus path 2
ratify-twelve-then-follow-up). On 2026-08-19 the Maintainer decided
both explicitly and in writing:

> F1 — Concrete interchange format for S04#8.3? → **F1-A: JSON**
>
> F2 — Sequencing path? → **F2-A: Revise RFC-0020, ratify all 13
> together** (= RFC-0020 sequencing path 1, revise-then-ratify)

This ADR is the authoritative record of those decisions and of the
acceptance of the revised RFC-0020 (Article 7; L-8 / INV-8), recorded
without addition (CN-14). It is the recording ADR of the Stage 1 W-B
amendment cycle (S04 §Sequence flows, step 2; INV-18).

## Decision

1. **F1 — the concrete interchange form is JSON (family F1-A).** A
   Stage 1 FSL artifact is exactly one JSON text as defined by
   RFC 8259 / ECMA-404, encoded per RFC 8259's interchange encoding
   rule (UTF-8). The choice is the Maintainer's; the recorded evidence
   basis (rationale, not authority): GL-15 boring-format guidance and
   DP-28 plainness; CN-26 (no proprietary or single-vendor tooling);
   the ratified stdlib-only Python 3.11 toolchain reads and writes
   JSON with no new dependency (TESTING_CONVENTIONS §1); JSON
   minimizes the S04#8.2 item d type/data-model risk among the
   admissible standard formats; and the repository's only existing
   serialized-data usage is JSON (non-authoritative build manifests).
   The ADR-0010 YAML decision covers the specification-index sidecar
   mechanism only and set no artifact-serialization precedent
   (verified by RFC-0020).

2. **F2 — sequencing path 1 (revise-then-ratify).** RFC-0020 is
   revised in this same decision cycle to draft S04#8.3 from the F1
   decision, and this single recording ADR ratifies all thirteen
   clauses together. No follow-up amendment cycle for S04#8.3 exists.

3. **RFC-0020 is accepted; the thirteen-clause Stage 1 W-B set is
   ratified.** The reviewed clause text of the revised RFC-0020 enters
   `specs/S04-language-definition.md` as the §Stage 1 clause set
   through the amendment path. Final clause identifiers are allocated
   exactly as proposed — S04#5.1, S04#5.2, S04#6.1, S04#6.2, S04#7.1,
   S04#7.2, S04#7.3, S04#7.4, S04#7.5, S04#7.6, S04#8.1, S04#8.2,
   S04#8.3 — and are frozen under the binding clause-numbering freeze
   (ADR-0009; S04#3.2): assigned exactly once, never renumbered.
   Categories: S04#7.5 is `unspecified`; every other clause is
   `defined`.

4. **`spec.version` remains `1.0.0` (F3 resolved by record, not
   silence).** ADR-0011 Decision 2 recorded 1.0.0 narrowly and
   established no specification-versioning policy; no recorded rule
   maps clause-set growth to a version change, and creating one here
   would invent versioning policy outside its own decision path
   (RFC-0009 window). The value is therefore recorded unchanged;
   future versioning policy travels its own RFC → ADR cycle.

5. **Ratified-text amendment — exact scope.** The S04 amendment
   consists of: the new §Stage 1 clause set (W-B interchange kernel)
   section; the status-header update ("Ratified (container: ADR-0009;
   Stage 0 contract clause set: ADR-0011; Stage 1 W-B clause set:
   ADR-0013)"); the Scope clause-content requalification; the
   Data-model language-content requalification; the
   Testing-requirements checker-coverage sentence extension; the
   Acceptance-criteria content-criteria requalification; and one
   Traceability row. No other ratified sentence changes. The sidecar
   gains the thirteen matching entries (ADR-0010 schema, clause-ID
   order, `status: ratified`). ADR-0009, ADR-0010, ADR-0011, and
   ADR-0012 are not modified.

6. **CN-9 recorded exception extended.** Per the ADR-0011 Decision 7
   mechanism, exactly as ADR-0012 anticipated: no conformance suite
   exists (G-CONF open; P12 gated), so CN-9 closure for the thirteen
   Stage 1 clauses is recorded as an explicit exception discharging
   when P12 produces clause-traced tests. Until then no test claims to
   verify a clause (TESTING_CONVENTIONS §4).

7. **Preserved without change:** the D3 type/data-model deferral (JSON
   serves as serialization only; no type/data-model semantics enter
   through it — S04#8.2 item d; S04#8.3); the D4 determinism
   requirement (ratified as S04#7.4); the namespace-token state
   (ADR-0008 — none ratified, none created); the RFC-0005 and
   RFC-0009 interim rules.

8. **Nothing else is decided.** No syntax or grammar; no type/data
   model; no execution-facing semantics (Stage ≥ 2); no conformance
   levels; no S05, S13, or CI-governance change; no compiler, runtime,
   or implementation authorization; no JSON schema, key set, or
   artifact-structure semantics beyond the ratified clause text — any
   concrete artifact schema over the JSON form is deferred, labeled
   territory travelling its own amendment cycle.

### Judgment calls disclosed (Baseline §12)

- **Identifier allocation:** the proposal-time identifiers are adopted
  unchanged as the final allocation, following the RFC-0018 → ADR-0011
  precedent; allocation is the recording act, and renumbering at
  ratification would create churn with no governing basis.
- **Standard citation:** JSON is identified by its defining standards
  (RFC 8259 / ECMA-404) as identification of the decided format, not
  as adoption of any additional policy; the UTF-8 encoding rule is
  RFC 8259's own interchange requirement, not a new repository rule.
- **S04#8.3 category:** `defined` — the clause is fully determined by
  the recorded F1 decision, leaving no latitude.
- **F3 disposition:** recording the unchanged `spec.version` value was
  chosen over inventing a bump rule; the alternative would establish
  versioning policy without a decision.
