# ADR-0008 — Namespace Registry Authority, Identifier Grandfathering, and Token Discipline (RFC-0002)

**Status:** Accepted
**Date:** 2026-08-11
**Decider:** Maintainer (Constitution Article 6)
**References:** RFC-0002, ADR-0004, ADR-0006, ADR-0007,
`docs/program/S04_CHARTER.md` §7 (PR #35), Baseline §13 (scalability
prerequisites), Doctrine DP-12 and CN-14, Blueprint §10, Issue #7

## Context

ADR-0004 ratified RFC-0002's recommendation — namespaced sequential
artifact identifiers with stable hierarchical clause IDs (N-B + N-C) —
but recorded neither of the two statements RFC-0002 requires of its
acceptance decision:

- **Open Question 1:** "Namespace registry: who ratifies new
  namespaces (ADR each, or a delegated register)?"
- **§Consequences:** "the acceptance ADR must state whether existing
  IDs are grandfathered (recommended by A-1) or migrated with a
  mapping table."

The S04 charter §7 (PR #35) recorded that gap as the open decision
surface blocking P03.2 and, transitively, P03.1 and P03.3–P03.5. On
2026-08-11 the Maintainer decided the surface explicitly and in
writing (directive decisions Q1 = A, Q2 = A, Q3 = B, recorded below).
Per Constitution Article 7, Baseline L-8, and INV-8, no decision is
binding until recorded as an ADR; this ADR is that record. It
introduces no option outside the recorded frame (CN-14), adds no
architecture, and ratifies no namespace token.

## Considered options

- **Registry authority** (RFC-0002 Open Question 1): an ADR for each
  namespace, or a delegated register.
- **Existing identifiers** (RFC-0002 §Consequences): grandfathered
  (recommended by A-1), or migrated with a mapping table.
- **Concrete namespace tokens** (charter §7 surface): ratify initial
  tokens in this act, or authorize the mechanism only and admit each
  token through its own governed decision.

## Decision

1. **Identifier architecture — unchanged.** N-B + N-C stands exactly
   as ratified by ADR-0004. This ADR records only the layering
   decision already present in the ratified frame: hierarchical
   dotted clause identifiers (N-C) layer on the namespace-capable
   document-identifier scheme (N-B). No clause ID is assigned here;
   no new implementation requirement is created.

2. **Namespace registry authority (directive Q1 = A).** Every new
   namespace requires its own RFC → ADR governance path. No delegated
   authority may create or ratify a namespace outside that path. The
   registry therefore has no standing document of its own: a
   namespace exists if and only if an Accepted ADR ratifies it, and
   the recording ADRs are the registry. A namespace never becomes
   authoritative by appearing in documentation, an implementation, a
   knowledge mirror, or a proposal (L-8/INV-8; L-9/INV-9).

3. **Existing identifiers (directive Q2 = A: grandfathered).** Every
   already-assigned identifier — RFC-NNNN, ADR-NNNN, the S<nn>
   specification files, and all other existing IDs — is
   grandfathered: it remains authoritative exactly as assigned, is
   never renumbered, and is never migrated (RFC-0002 A-1). The
   namespace-capable scheme applies prospectively only. No migration
   is performed, so no mapping table exists; creating one would
   record a migration that was decided against.

4. **Concrete namespace tokens (directive Q3 = B: none ratified).**
   This ADR ratifies no concrete namespace token. The tokens
   appearing inside RFC-0002's design-space examples are illustrative
   only and are not ratified by this or any prior decision. Each
   future concrete token enters through its own RFC → ADR decision
   per decision 2: a proposal RFC names the token and its scope; the
   Maintainer's recording ADR ratifies it; the token is authoritative
   from that ADR forward and never before. No token is selected
   silently or by convenience.

5. **RFC-0002 Open Questions 2 and 3 — preserved open.**
   - **OQ2** (do workspace mirrors display repo IDs verbatim): not
     decided here. Standing L-9 practice (one-way derived mirror)
     continues; a decision requires its own recorded path.
   - **OQ3** (clause-numbering freeze point: ratification or first
     citation): not decided here. The ratified N-C rule already binds
     as a lower bound — clauses may not renumber after ratification
     (ADR-0004) — and the S04 container text "Clause IDs freeze at
     ratification" is In Review, not ratified. The freeze point
     becomes binding with the S04 container ratification (P03.1).

## Consequences

- **P03.2 unblocks.** S04's document identifier is the grandfathered
  `S04` (decision 3), and N-C clause identifiers layer on it
  (decision 1), so the identifier scheme's spec text can be recorded
  in S04 with no namespace token. That is specification work and
  travels its own P03 PR (ADR-0004 consequence; ADR-0007 follow-up 2),
  not this governance-only change.
- **P03.1** requires the merged P03.2 scheme text plus its own
  recorded ratification (Article 7; G-SPEC(S04)) — a Maintainer
  decision.
- **P03.3** remains specification work: no recorded decision
  enumerates the Stage 0 clause inventory, so no clause ID is
  derivable today; drafting travels Draft → In Review → per-clause
  ratification (PROGRAM.md P03 acceptance gates).
- **P03.4 and P03.5** remain blocked: the M-B index schema is decided
  at first specification ratification (RFC-0008; ADR-0004).
- The charter §7 decision-surface record and the `docs/rfc/README.md`
  provisional-numbering note are superseded by this record and update
  in this same change (program record, Blueprint §7; register per the
  ADR-0004 convention). RFC-0002's file keeps its submission-time
  `Status: In Review` header; the index plus the deciding ADRs remain
  the authoritative disposition record.
- **No implementation is authorized by this ADR.** CN-14 and the
  G-SPEC gates stand.
