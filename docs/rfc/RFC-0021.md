# RFC-0021 — S05 Compiler Subsystem Boundary Contract Specification

**Status:** In Review · **Date:** 2026-08-19 · **Author:** Hermes Agent · **Decision target:** Maintainer (Constitution Article 6, Article 7)

---

## 1. Summary

This proposal specifies the initial **S05 Compiler Subsystem Boundary Contract**, unblocking the implementation program **P04 (Compiler)** under the ratified Stage 1 W-B interchange kernel (`S04#5.1`–`S04#8.3`, ratified via ADR-0013).

Following the zero-invention discipline (INV-2, INV-3, INV-17) and boring-tooling principle (GL-15, DP-28), this proposal establishes:
1. **Invocation Boundary:** A deterministic CLI command and Python programmatic API consuming ratified S04 JSON interchange artifacts (`S04#8.3`).
2. **Validation & Diagnosis Contract:** Strict machine-readable diagnostic schema linking compiler rejection events directly to violated ratified S04 clause identifiers (`S04#6.1`–`S04#7.6`).
3. **Stage 1 Artifact Emission Contract:** A deterministic validation bundle output format (`.fcos-bundle.json`) recording the validated artifact graph and compiler metadata.
4. **Deferred Functionality:** Explicit non-scope for executable bytecode generation, type system semantics, runtime ABIs, and package management (deferred to Stage ≥ 2).

---

## 2. Motivation & Upstream Context

With the ratification of the Stage 1 W-B Interchange Kernel (ADR-0013; 13 clauses `S04#5.1`–`S04#8.3`), the project has an authoritative, concrete interchange format for Frontier Specification Language (FSL) artifacts in JSON (`S04#8.3`).

However, compiler implementation (**P04**) is currently **GOVERNANCE-BLOCKED** by:
- **`G-SPEC(S05)`:** Ratification of `specs/S05-compiler.md` boundary contracts.
- **`B-06`:** Interface forms UNKNOWN (specifically the compiler boundary contract).
- **`B-08`:** Specifications remain unratified except S04.

`specs/S05-compiler.md` has remained in `Status: In Review` with all interface, error model, and artifact emission sections marked `BLOCKED pending S4 specs`. This RFC drafts the exact minimal normative boundary specification for S05, enabling its formal ratification via an ADR and unblocking P04.

## 3. Normative S05 Boundary Specification Proposal

### 3.1. Input Acceptance Contract

1. **Input Format (`S05#1.1`):** The compiler shall accept as primary source input a UTF-8 encoded file containing a single JSON object conforming strictly to the ratified S04 Stage 1 W-B interchange specification (`S04#5.1`–`S04#8.3`).
2. **Schema Validation (`S05#1.2`):** The compiler shall immediately validate that the input object contains `schema_version` matching `"fsl/1.0"` (`S04#8.3`). Any mismatched or missing schema version shall cause immediate rejection citing `S04#8.3`.
3. **Deterministic Parse (`S05#1.3`):** Parsing of JSON input must follow strict RFC 8259 syntax without extensions. Duplicate keys within any JSON object shall be rejected as invalid input citing `S04#8.3`.

### 3.2. Validation & Diagnostic Error Contract

1. **Clause-Traceable Diagnostics (`S05#2.1`):** When the compiler rejects an input artifact, it must emit machine-readable diagnostics. Every diagnostic representing a specification violation must cite the exact ratified clause identifier (`S04#6.1`–`S04#7.6`, `S04#8.3`) governing the failure (INV-17).
2. **Diagnostic Structure (`S05#2.2`):** Each diagnostic entry shall contain:
   - `code`: String identifying the diagnostic category (`"SYNTAX_ERROR"`, `"VALIDATION_ERROR"`, `"DEPENDENCY_ERROR"`, or `"INTERNAL_ERROR"`).
   - `clause_id`: String containing the governing ratified clause ID (e.g. `"S04#6.2"`), or `null` for internal I/O errors.
   - `message`: Human-readable explanatory description.
   - `path`: JSON pointer / dot-path string to the offending field (e.g. `"manifest.dependencies[0]"`).
3. **Deterministic Diagnostic Ordering (`S05#2.3`):** Diagnostic lists must be sorted deterministically by JSON path, then by clause ID, ensuring identical diagnostics output across environments for identical invalid inputs.
4. **No Semantic Inventions (`S05#2.4`):** The compiler shall not emit diagnostics asserting behavioral or semantic constraints not ratified in S04 (INV-3, Baseline §6).

### 3.3. Invocation & CLI Contract

1. **CLI Entry Point (`S05#3.1`):** The compiler CLI shall be invokable via:
   ```bash
   fcos-compile <input-artifact.json> [--out <output-path>] [--format json|text]
   ```
2. **Exit Codes (`S05#3.2`):**
   - `0`: Compilation / validation successful; output artifact emitted.
   - `1`: Input validation or specification conformance failed (diagnostics emitted to `stderr` or structured output).
   - `2`: Invocation / CLI usage error (e.g. missing input file, unreadable path).
   - `3`: Internal unhandled compiler fault.
3. **Standard Programmatic API (`S05#3.3`):** The compiler must provide an importable Python API:
   ```python
   def compile_artifact(source_data: dict | str, options: dict | None = None) -> CompilationResult:
       ...
   ```
   where `CompilationResult` contains `success: bool`, `diagnostics: list[Diagnostic]`, and `bundle: ExecutionBundle | None`.

### 3.4. Output Emission Contract (Stage 1 Scope)

1. **Stage 1 Output Target (`S05#4.1`):** In Stage 1, compilation consists of full structural validation and dependency resolution. The output emitted is a deterministic **Execution Bundle** JSON document (`.fcos-bundle.json`).
2. **Execution Bundle Structure (`S05#4.2`):** The bundle must contain:
   - `bundle_version`: `"1.0.0"`
   - `compiler_version`: String containing the compiler version.
   - `artifact`: The validated FSL artifact payload.
   - `resolved_dependencies`: List of resolved dependency IDs.
   - `compilation_timestamp_utc`: Deterministic ISO timestamp (or fixed epoch in reproducible builds).
3. **Determinism Guarantee (`S05#4.3`):** Given identical input bytes and identical compiler version, the output bundle bytes must be byte-for-byte identical (reproducibility rule, DP-28).

## 4. Deferred Design Surfaces (Explicit Non-Scope)

1. **Executable Codegen & Bytecode:** Deferred to Stage ≥ 2 (dependent on S06 Runtime specification).
2. **Type System Typechecking:** Deferred (S04#4.1 / ADR-0012 D3 deferred the type model).
3. **Module & Package Resolution from Remote Registries:** Deferred (S11 Deprecated; S04#3.1 local scope).
4. **Optimization Envelope & IR Passes:** Deferred (optimization must operate over executable IR, which does not exist in Stage 1).

## 5. Drawbacks, Alternatives & Decisions to be Recorded

| Decision Topic | Proposed Choice | Alternative Considered | Tradeoff / Rationale |
|---|---|---|---|
| **Invocation Surface** | Dual (CLI + Python API) | CLI-only or API-only | Dual surface serves both CLI workflows (P01 gates, shell usage) and embedded tools/testing (`tests/test_compiler.py`) with zero overhead. |
| **Output Target** | Validated Execution Bundle JSON | AST-only JSON or no output (validation-only exit code) | Emitting a bundle preserves the Stage 1 artifact contract while providing concrete data for downstream tooling without inventing runtime bytecode. |
| **Diagnostics Format** | Structured JSON with `clause_id` pointer | Free-form text diagnostics | Machine-readable `clause_id` ensures mechanical traceability and integration with P12 conformance suites. |

## 6. Downstream Impact & Program Unblocking

- **Discharges:** `G-SPEC(S05)` (upon ADR ratification), partially discharges `B-06` (compiler boundary interface).
- **Unblocks:** `P04.1` (Compiler harness & implementation plan) and `P04.2` (Skeleton + diagnostics plumbing).
- **Preserves:** 100% boundary isolation from historical Phase 0 prototype code (`tools/compiler/fcos/`).
