# RFC-0012 — Runtime Scope

**Status:** In Review · **Date:** 2026-08-02 · **Resolves:** U-14
**Subsystem:** S6 Runtime · **Decision blocked by RFC-0001 (D-01)**

## Summary

Decide what S6 Runtime *is*: the Blueprint records the subsystem's
existence but marks its scope UNKNOWN. The design space ranges from "no
runtime at all" to a full execution environment, and the choice is almost
entirely determined by RFC-0001's identity outcome.

## Motivation

U-14; the WP17 prompt (Engineering Prompt Library) is classified
RFC-preparation for exactly this reason. Recording the scope space now
prevents the runtime from being defined implicitly by whatever the first
implementation happens to execute (CN-14, R-4 analogue).

## Assumptions

- A-1: If a runtime exists, its observable behavior is spec-defined and
  it holds zero defining authority (L-2, L-3).
- A-2: "Runtime" here means the execution-time subsystem, not the
  compiler (S5) and not tooling (S9).

## Design Space (conditional on RFC-0001)

| # | Scope | Coherent with identity | Trade-offs |
| --- | --- | --- | --- |
| S-A | No runtime: artifacts are consumed by external tools; S6 is retired by Baseline amendment | I-A (definition language) | Smallest system; retirement is an architecture change requiring the §13 amendment path |
| S-B | Validation/evaluation runtime: executes checks, queries, and derivations over artifacts | I-A/I-D | Modest surface; boundary with S13 conformance tooling must be drawn precisely |
| S-C | Full execution environment (scheduling, I/O, resource model) | I-B/I-C | Largest surface; dominates the RFC roadmap; the Phase 2 45–70 RFC estimate mostly lives here |

## Open Questions

1. If S-A, which subsystem owns the tool-facing evaluation semantics
   that S-B would have owned — or is that out of scope entirely?
2. If S-B/S-C, is the runtime's diagnostic surface part of the
   compatibility promise (RFC-0005 Q1)?
3. Host-language question: the runtime's implementation language is an
   implementation choice with zero spec authority — but does governance
   constrain it for maintainability (single-maintainer reality, OB-4)?

## Consequences

Not decidable before RFC-0001; this RFC pre-commits the decision space so
that RFC-0001's acceptance ADR can resolve U-14 in the same act or
explicitly re-defer it with a review point.

## Recommendation (non-binding)

Resolve U-14 inside RFC-0001's acceptance ADR rather than as a separate
later decision — the two are one identity choice viewed twice.
