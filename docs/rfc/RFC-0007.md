# RFC-0007 — Package Distribution Model

**Status:** In Review · **Date:** 2026-08-02 · **Resolves:** U-8
**Subsystem:** S11 Package Manager · **Decision blocked by RFC-0001 (D-01)**

## Summary

Decide whether FCOS needs a package manager and registry at all
(Blueprint marks S11 necessity UNKNOWN), and if so, the distribution
model's frame: naming, versioning interaction, yanking, and trust.

## Motivation

U-8. Blueprint §2 records S11 with "necessity UNKNOWN" — the only
subsystem whose existence is conditional. The necessity question is
prior to every design question and is itself D-01-dependent (a
definition-language identity may need only document distribution).

## Assumptions

- A-1: The package manager never changes what resolved code means
  (Baseline §4 forbidden responsibility).
- A-2: Package identity interacts with RFC-0002 namespaces and U-10
  versioning; those decisions constrain this one.

## Design Space

**Necessity:** (N-yes) ecosystem distribution is in scope; (N-no)
distribution reduces to repository/release artifacts; (N-defer) recorded
deferral with review at RFC-0001 acceptance.

**If N-yes, model frame:** central registry vs federated/namespaced
registries vs repository-direct (URL) resolution. Trade-offs: central =
simplest trust story, single point of governance and failure; federated =
scales governance, complex trust and name arbitration; repo-direct =
zero infrastructure, weakest immutability and yanking guarantees.

## Open Questions

1. Immutability: are published packages permanently immutable with
   yank-as-status (Blueprint §7 lifecycle suggests yes)?
2. Who may publish under which namespace (RFC-0002 interaction)?
3. Supply-chain trust: signing and provenance requirements — frame only,
   no tooling selection (CN-26).

## Consequences

Only N-defer is honestly decidable before RFC-0001; this RFC exists so
the deferral is recorded rather than implicit (DP-15, CN-14).

## Recommendation (non-binding)

N-defer with mandatory review inside RFC-0001's acceptance ADR.
