# RFC-0022 — S13 Verification & Conformance Subsystem Specification

**Status:** In Review · **Date:** 2026-08-19 · **Author:** Hermes Agent · **Decision target:** Maintainer (Constitution Article 6, Article 7)
**Governing Ratifications:** S04 Stage 0 (ADR-0011), S04 Stage 1 W-B (ADR-0013), S05 Compiler Boundary (ADR-0014)
**Frame Dispositions:** RFC-0004 (L-A + C-A, accepted per ADR-0004), RFC-0008 (M-B, accepted per ADR-0004 / ADR-0010)

---

## 1. Summary

This proposal specifies the initial **S13 Verification & Conformance Subsystem Specification**, defining the normative architecture, harness boundary, evidence evaluation model, and official conformance claim regime for Frontier Creative OS.

With the completion of **P04 Stage 1 (P04.0–P04.5)**, the FSL Stage 1 W-B compiler implementation (`tools/compiler/fsl/`) has produced comprehensive spec-derived test evidence (`docs/program/P04_4_SPEC_DERIVED_TEST_EVIDENCE.md`) and submitted its baseline to the P12 frame (`docs/program/P04_5_CONFORMANCE_SUBMISSION.md`). 

This RFC bridges the engineering verification delivered in P04/P11 with the formal conformance judging required by **P12 (Verification & Conformance)**, enabling the unblocking of:
1. **`G-SPEC(S13)`:** Formal ratification of `specs/S13-verification-conformance.md`.
2. **`P12.2`:** Implementation of the independent Conformance Test Harness (`tools/conformance/`).
3. **`P12.3`:** Formalization of the normative Conformance Fixture Corpus (`tests/fixtures/conformance/`).
4. **`P12.4`:** Execution of the Sole Conformance Judge (INV-16) and issuance of auditable Conformance Claims (`docs/conformance/claims/`).
5. **`G-CONF`:** Eventual closure of the global conformance gate prior to versioned releases (Article 9).

## 2. Motivation & Upstream Governance Alignment

### 2.1. The Conformance Principle (INV-16 & Baseline §10)
Per **Blueprint INV-16** and **Baseline §10**:
> *"The conformance suite, not any implementation, is the sole judge of conformance. No implementation, test suite, or maintainer opinion substitutes."*

Implementation test suites (such as `tests/compiler/`) provide engineering verification that code matches developer intent. However, per **S04#7.6** and `docs/program/CONFORMANCE_FRAME.md`, implementation test passage does **not** constitute an official conformance judgment.

### 2.2. Discharged Prerequisites
The prerequisites identified in `specs/S13-verification-conformance.md` are now fully satisfied:
- **Ratified Language Specification:** S04 Stage 0 (12 clauses, ADR-0011) and S04 Stage 1 W-B (13 clauses, ADR-0013) are ratified with machine-readable clause indices (`specs/S04-language-definition.index.yaml`).
- **Ratified Compiler Boundary:** S05 Compiler Subsystem Boundary Contract (13 clauses, ADR-0014) is ratified with strict input, diagnostic, invocation, and output contracts (`specs/S05-compiler.index.yaml`).
- **Harness Boundary Unblocked:** S05 defines the standard CLI invocation (`fcos-compile`) and exit code protocol (`0`, `1`, `2`, `3`), establishing the mechanical driver interface required for the conformance harness.

## 3. Normative S13 Specification Proposal

### 3.1. Conformance Model & Labeling (`S13#1.1`–`S13#1.3`)

1. **Sole Judge Authority (`S13#1.1`):** Conformance to FSL specifications is judged exclusively by the S13 Conformance Test Harness executing against ratified specification clauses (INV-16).
2. **Binary Conformance Model (`S13#1.2`):** Per the accepted RFC-0004 **L-A** disposition (ADR-0004), conformance is binary (`CONFORMING` vs `NON_CONFORMING`) for a given specification version. No partial conformance levels, tiers, or profiles exist in Stage 1.
3. **Clause Totality (`S13#1.3`):** To achieve `CONFORMING` status for a specification version, a candidate implementation must satisfy 100% of the active, testable ratified clauses for that version without exception.

### 3.2. Conformance Harness Boundary Contract (`S13#2.1`–`S13#2.4`)

1. **Black-Box Invocation (`S13#2.1`):** The conformance harness shall drive candidate implementations exclusively through their ratified public invocation boundaries (e.g. S05 CLI `fcos-compile` or standard programmatic API `compile_artifact`). The harness shall not inspect or depend on implementation internals (L-4, Blueprint §3).
2. **Standard Harness Interface (`S13#2.2`):** Candidate tools must accept standard input interchange files (`.fsl.json`) and emit standard exit codes and execution bundles (`.fcos-bundle.json`) or structured diagnostics.
3. **Deterministic Harness Execution (`S13#2.3`):** The harness must execute fixture suites in a deterministic, isolated environment, ensuring identical verdict outcomes across platforms (DP-28).
4. **Reproducible Test Reporting (`S13#2.4`):** Harness output shall consist of a structured, machine-readable Conformance Evaluation Report (`conformance-report.json`) detailing per-clause evaluations, fixture inputs, observed exit codes, and diagnostic match verifications.

### 3.3. Conformance Fixture Corpus Contract (`S13#3.1`–`S13#3.4`)

1. **Clause-Traced Fixtures (`S13#3.1`):** Every fixture in the normative corpus (`tests/fixtures/conformance/`) must carry metadata explicitly tracing it to one or more ratified clause IDs (CN-9 discipline).
2. **Dual-Corpus Requirement (`S13#3.2`):** Every testable clause must be covered by:
   - At least one **Positive Fixture** (valid input demonstrating required acceptance and correct output structure).
   - At least one **Negative Fixture** (invalid input demonstrating mandatory rejection and exact clause-attributed diagnostic emission).
3. **Fixture Immutability (`S13#3.3`):** Conformance fixtures are version-pinned to specification revisions. Modifying fixture expectations requires an explicit specification amendment cycle.
4. **Synthetic Independence (`S13#3.4`):** Fixtures must be authored directly from specification prose and sidecars, completely independent of implementation code.

### 3.4. Conformance Claim & Certification Regime (`S13#4.1`–`S13#4.4`)

1. **Self-Certification Protocol (`S13#4.1`):** Per the accepted RFC-0004 **C-A** disposition (ADR-0004), conformance claims are issued via self-certification backed by published, reproducible evidence dossiers.
2. **Claim Structure (`S13#4.2`):** A formal Conformance Claim document (`docs/conformance/claims/<impl>-<version>-<spec>-<spec_version>.json`) must record:
   - Candidate implementation name, commit SHA, and release version.
   - Target specification identifier and ratified version (e.g. `S04` v1.0.0, `S05` v1.0.0).
   - Conformance harness version and SHA-256 hash.
   - Comprehensive verdict (`CONFORMING` / `NON_CONFORMING`).
   - Summary of evaluated clauses (total, passed, failed, omitted).
   - SHA-256 digest of the complete Conformance Evaluation Report.
3. **Claim Invalidation (`S13#4.3`):** A standing claim is invalidated if:
   - A new specification version is ratified (requiring re-certification).
   - A verified specification divergence is discovered (constituting a defect under L-2).
4. **Public Registry (`S13#4.4`):** All asserted claims are recorded immutably in the repository's conformance registry.

## 5. Explicit Non-Scope & Deferred Decisions

1. **Graded Conformance Levels (Core vs Full):** Deferred per RFC-0004 / ADR-0004. Binary model is enforced for Stage 1.
2. **Third-Party Certification Authorities:** Deferred per RFC-0004 C-A.
3. **Runtime & Dynamic Execution Conformance:** Deferred to Stage ≥ 2 (dependent on S06 Runtime specification).
4. **Performance Budgets & Benchmarking:** Deferred per WBS P11.4 / B-10 (no quantitative performance requirements ratified).
